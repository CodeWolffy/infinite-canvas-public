下述风险证据保留修复前的利用条件，当前实现状态以修复状态和待测试清单为准。未对真实商户、上游或生产站点执行攻击请求；补充修复使用无害标记、临时数据库和测试 Redis 验证。不能据此认定生产站点已经被利用。

## SEC-01：已开始消费的任务仍可全额退款

证据：

- `server/internal/platform/generation.go` 的 `cancelTask` 对 `reviewing`、`queued`、`running` 统一执行 `changeWallet(..., "release", ..., price, -price, ...)`，随后清除 worker 租约并标记取消。
- `server/internal/platform/text_stream.go` 的 `appendText` 已持续保存并推送 `partial_text`；`textEvents` 和 `textRequestDetail` 在任务尚未结算时即可返回文本。
- `server/internal/platform/worker.go` 对用户取消直接退出，不再结算已消费部分；取消函数也把进行中的上游成本记录标记为 `canceled`。
- 异步视频提交成功后由 worker 保存 `upstream_task_id` 并重新设为 `queued`。这种排队任务已经提交上游，不能按“尚未开始消费”判断；当前取消流程没有上游任务撤销与退款确认。

利用方式：用户收到所需的部分文本后取消，保留结果并取回全部冻结余额，再发起下一次请求；视频任务也可在上游接受后取消并取回冻结额。HTTP 请求中断不代表供应商撤销已发生的费用，实际损失取决于渠道对中断与异步任务的收费规则。现有 RPM 只限制消耗速度，不能防止重复使用同一笔余额。

修复方向：按是否已提交上游、是否已有输出和已消费用量区分取消结算；未开始的任务才可直接全退。已提交异步任务必须核对供应商撤销结果；保留中断任务的真实成本与取消原因。需要先明确运行中取消、缺少 usage 和供应商无法取消时的扣费规则。

验收要求：隔离上游分别模拟未提交取消、已有文本输出取消、已接受异步视频取消；客户端保留输出时不能无限循环全额退款。并发取消与完成只能结算一次，账本、任务、上游成本记录保持一致。

## SEC-02：不可信时长与补扣封顶形成低价消费路径

证据：

- `server/internal/platform/pricing.go` 的 `pricingSnapshot` 对音频、视频均读取用户的 `seconds`／`durationSeconds`，按其计算冻结金额，只要求时长为正数。
- `server/internal/platform/upstream.go` 的音频 `audio/speech` 请求只选取 voice、speed、instructions、response_format；用户声明的秒数不限制实际合成长度。
- `server/internal/platform/worker.go` 在音频完成后通过 `audioDuration` 获取真实时长，计算实际金额；`finishTask` 遇到余额不足补扣时把 `charge` 设回冻结额，并仍按成功交付结果。
- 同样的免差额逻辑适用于文本。`promptEstimate` 使用文本字节数除以 4，加固定估算；没有计入图片附件的实际 token 用量。
- 现有 `operations_test.go` 的 `insufficient_extra_matches_ledger` 明确把“实际费用高于冻结额且余额不足时只扣冻结额”作为预期。仅保持当前测试通过不能消除此风险。

音频示例（示意配置，不代表生产价格）：单价为每秒 ¥0.01、单次保底为 0，用户声明 `0.000001` 秒，只需冻结 1 微元。若真实音频为 60 秒，应收 ¥0.60，但账户只有 ¥0.01，结算会只收取原冻结的 1 微元，仍可获取完整音频。较高的固定保底可以缩小这个差距，但没有消除信任用户时长的问题。

修复方向：音频冻结预算应由服务端根据实际输入和可信的生成约束确定；文本预算需覆盖图片及所选模型的计费方式。通过足额冻结、增量冻结或在预算用尽时停止生成，避免把余额不足直接变成免单。若产品确实要补贴差额，应将其作为明确的补贴策略，而非隐含结算分支；相关行为需要先确认。

验收要求：按秒音频携带极小时长、长文本、较慢语速和低余额时，不能低额冻结后免费交付高成本结果；文本覆盖图片、高 token 密度输入及多任务同时冻结余额的场景；结算与取消竞态均不能少扣或重复扣款。

## SEC-03：高危操作的等效入口遗漏二次验证

证据：

- `server/internal/platform/security.go` 已有 `requireSecurityProof`，核对管理员密码与已启用的 MFA。
- `server/internal/platform/admin.go` 的修改角色接口调用该校验，但 `POST /api/admin/users` 直接接受 `role=admin` 和攻击者选择的临时密码，没有二次验证。
- `server/internal/platform/wallet.go` 的余额调整要求二次验证；`server/internal/platform/groups.go` 的 `POST /api/admin/redeem-codes` 却可直接发行指定金额的兑换码并返回完整码。

利用方式：持有管理员会话的攻击者可以先建立自己的管理员账号，登录并完成首次改密，再用自己知道的密码通过高危操作验证；也可以直接发行兑换码，在自己的普通账号兑换余额。这使“只有 Cookie、不知道密码／MFA 时不能操作资金”的防线失效。没有证据表明普通账号可绕过管理员路由鉴权。

修复方向：创建管理员、发行有价值兑换码等与提升权限／调整余额等效的入口，应复用同一二次验证；同时核查模型价格、折扣、分组等可等效开放免费消费的配置入口。校验须发生在业务写入事务中，错误凭据不能产生账户或兑换码，审计不能记录密码、验证码和完整兑换码。

验收要求：仅有管理员 Cookie，缺少或使用错误的密码／MFA 时，新建管理员和发行兑换码均失败；正确凭据才可完成。常规角色变更和直接余额调整的保护继续有效。

## SEC-04：修改渠道地址可间接导出服务端 Key

证据：

- `server/internal/platform/admin.go` 的渠道保存允许修改现有 `base_url`，没有 `requireSecurityProof`；`apiKeys` 为空时继续保留原 `channel_keys`。
- 同文件的 `POST /api/admin/channels/:id/models` 会读取渠道并调用 `selectChannelKey`，随后向配置的 Base URL 请求模型列表。
- `server/internal/platform/upstream.go` 的 `authorize` 把原 Key 放进 Authorization、x-api-key 或 x-goog-api-key；`channel_keys.go` 在服务端解密该 Key。
- `media.go` 的安全 HTTP 客户端可以阻断内网地址和带密钥的跳转，但攻击者拥有正常公网 HTTPS 服务器时，直接修改目的地址即可，不需要重定向。

利用方式：管理员会话被盗后，攻击者把已有渠道的 Base URL 改为自己的 HTTPS 地址，触发拉取模型列表，即可在接收端获得原有 Key。攻击者随后可直接消耗供应商账户余额，绕过平台钱包和用户频控。数据库加密与浏览器不回显 Key 不能阻止这条路径。

修复方向：渠道目的地址／协议等会改变凭据发送对象的修改应要求二次验证，并明确已有密钥是否可继续授权给新目的地址；不能静默复用。对现有渠道修改目的地址记录可追溯的审计，但不记录凭据。

验收要求：在两个隔离的测试上游之间切换地址，未完成二次验证时第二个上游收不到原 Key；未经明确授权的旧密钥不能随目的地址改变而继续发送。

## SEC-05：超大指数金额可耗尽 API 资源

证据：

- `server/internal/platform/payments.go` 在查询渠道和执行金额上限判断之前调用 `amountUnits(input.Amount, 100)`；金额仅校验字符串非空。
- `server/internal/platform/wallet.go` 的 `amountUnits` 先用 `decimal.NewFromString` 解析，再执行 Truncate、String，最后才通过 `strconv.ParseInt` 判断整数范围。
- 已核对本机 `shopspring/decimal v1.4.0` 源码：允许 32 位指数；String／rescale 会展开十进制数，调用 `big.Int.Exp` 等高成本操作。很短的极大指数输入即可触发远大于请求体大小的运算。
- HTTP 请求上下文的超时不能抢占这类未检查上下文的纯 CPU／内存运算；容器内存限制也只是限制损失范围，不能让请求安全失败。

利用前提：只需普通登录账号，不需要有余额或知道真实渠道 ID；提供格式正确的 UUID 即可先到达金额转换。巨大正指数在字符串展开时消耗资源，巨大负指数也可能在截断／对齐精度时触发高成本运算。此问题是服务可用性风险，不是整数溢出直接增加余额的结论。

修复方向：在任意精度运算前验证业务允许的金额表示形式和可表示范围，避免先展开再拒绝；时长及其他用户可控十进制入口一并检查，继续沿用成熟十进制库。若引入新的字符串长度、指数或数值边界，先明确适用入口、允许值和拒绝方式。

验收要求：以受限子进程或隔离容器覆盖正／负巨大指数，快速返回参数错误且内存可控；保留合法金额、分／微元精度和范围边界的行为。不得向生产服务发送可能造成资源耗尽的输入。

## SEC-06：支付下单与主动查单缺少业务频控

证据：

- `server/internal/platform/wallet.go` 的下单和 refresh 路由没有使用 `rateLimit`；对应 `createPaymentOrder`、`refreshPaymentOrder` 内也没有 `rate`。
- 下单幂等键按请求 UUID 去重，每个新 UUID 仍可创建新的未付款订单；Redis 创建锁仅针对单个订单，不能限制不同订单。
- pending 订单每次 refresh 都会执行真实网关查单，没有按订单合并进行中的查询。
- `worker.go` 的过期订单对账每轮读取并处理 100 条；持续制造未支付订单可增加数据量及后续查单压力。仓库中的 Nginx 配置没有此处的请求频控，生产外层 1Panel 是否另行限制尚未核实。

影响：不直接伪造到账，但可占用数据库、API 和支付网关调用能力，拖慢真实订单查账；外层统一 IP 限流不能完全替代按用户、按订单的保护。

修复方向：分别设计下单与查单的账号／IP 频控、待支付订单数量策略和同订单查询合并；合法支付回调仍需允许供应商重试，不能套用用户登录要求。新阈值应由用户确认，不能静默使用经验默认值。

验收要求：重复 UUID 不重复下单；多个 UUID 和并发 refresh 受已确认的边界限制；网关失败与重试不会造成重复入账，正常支付通知和迟到到账继续可处理。

## SEC-07：链接参数可把登录浏览器接到攻击者控制的 Agent

证据：

- `web/src/components/agent/local-agent-panel.tsx` 以 `agentUrl` 和 `agentToken` 查询参数触发自动连接；`web/src/components/agent/hooks/use-agent-connection.ts` 只验证 URL 使用 HTTP(S)，随即静默连接，并把 `confirmTools` 设为 `false`。
- Agent 握手成功后，前端通过 `postState` 向所选端点发送当前画布快照；`tool_call` 事件直接进入工具处理。画布写入确认被关闭，站点工具如 `workbench_video_generate` 也可发起付费生成。
- `canvas-agent/src/server/http.ts` 的 CORS 逻辑在请求带有有效 Token 时自动把请求来源加入允许列表。参数中的 URL 和 Token 都由链接提供者控制；攻击者自己的 Agent 可正常回送站点允许的 CORS 响应。

攻击前提：用户已登录平台并打开特制链接；泄露内容取决于当时是否有画布上下文。已确认的是代码可形成自动连接、状态发送和工具调用链，尚未用真实浏览器完成端到端攻击验证，也没有证据表明可仅凭远程请求绕过用户打开链接这一前提。由于 URL 可使用 HTTP，HTTPS 页面到不安全端点会受浏览器混合内容策略影响；外部攻击端需要使用 HTTPS。

影响：未提示用户就把画布内容交给链接指定的服务，并可能消耗用户钱包余额或使用其已登录站点执行工具操作。该信任边界与“只连接用户自己的可选本地 Agent”设计不符。

修复方向：链接只填充待审核的 Agent 地址，不得静默连接；连接前明确展示目标域名并由用户确认。链接连接的远程 Agent 应默认要求逐次确认敏感工具，尤其是生成、素材访问与画布读取；拒绝 HTTP 远程端点。验收时用本地隔离恶意 Agent 模拟画布读取、任意导航和付费生成，未确认前均不得发送状态或执行操作。

## SEC-08：公开画布分享可读取隐藏聊天附件

证据：

- `server/internal/platform/sharing.go` 的 `publicCanvasSnapshot` 会移除 `chatSessions` 和 `activeChatId`，所以公开 API 的 JSON 不包含助手聊天记录。
- 画布保存通过 `extractMediaIDs(input.Snapshot)` 从整份快照同步媒体引用，包含聊天会话引用的文件。
- 公开媒体路由只要找到任意 `owner_kind='canvas'` 的引用就允许访问，并读取媒体对象返回文件；这里没有检查媒体 ID 是否也属于已隐藏的聊天内容。

攻击前提：所有者主动创建并分享含有附件的画布；访问者还需已知目标附件的媒体 ID。公开快照没有列出隐藏附件的 ID，本轮未找到仅凭分享链接枚举这些 ID 的入口；这是授权边界不一致，不是可枚举所有聊天附件的结论。若同一文件也被画布的可见节点使用，文件本身本已公开；风险只适用于因聊天引用而进入引用集、但内容应随聊天隐藏的附件。

影响：隐藏聊天文本和会话元数据，但附件文件仍可能通过分享 API 泄露，造成隐私与资料外泄。

修复方向：分享时按公开快照派生允许访问的媒体集合，排除仅由聊天会话引用的附件；不要用源快照的全量引用授权。验收时分别验证仅在聊天中、同时在可见节点中、仅在节点中引用的媒体访问结果，并覆盖公开分享与撤销。

## SEC-09：Windows Claude CLI 提示词可注入命令

证据：

- `canvas-agent/src/agent/claude.ts` 将完整提示词作为子进程参数，并在 Windows 使用 `shell: true` 调用 CLI。Windows 命令行经 `cmd.exe` 解析，提示词中的 `&` 等元字符会成为命令分隔符。
- 本机隔离探针只运行了无害 `echo` 标记，确认 `&` 后的第二条命令会被执行；未在真实用户目录或生产环境执行命令。

## SEC-10：Skill frontmatter 解析会执行 JavaScript

证据：

- `canvas-agent/src/skills/store.ts` 使用 `gray-matter@4.0.3` 默认解析 `SKILL.md` frontmatter；读取、更新和删除前都会调用 `matter(raw)`。
- 创建和更新时调用的 `matter.stringify` 也会先解析输入正文；隔离探针确认 JavaScript frontmatter 会在最终抛出“不支持序列化 JavaScript”错误之前执行。读取时同样执行。探针只修改进程内的标记，没有读取用户文件或执行外部命令。

攻击前提：用户在已授权本地 Agent 中保存带恶意 frontmatter 的不可信正文，或攻击者令工作区中出现恶意 Skill 文件并诱导用户读取、更新或删除。Agent 服务只监听回环并要求 Token；本轮没有验证匿名远程可达性，也没有证明普通平台资产上传可进入本地 Skill 目录。

影响：在本机 Agent 进程权限下执行代码，可能读取工作区和本机用户可访问的数据。

修复方向：显式限制 frontmatter 语言及解析引擎为安全 YAML，禁用 JavaScript 引擎；序列化时将正文作为纯内容，避免再次自动解析其中的 frontmatter。验收应使用无害哨兵副作用检查读取、创建、更新、删除路径均不执行代码，同时维持合法 YAML frontmatter。

## SEC-11：ZIP 导入可触发浏览器资源耗尽

证据：

- `web/src/lib/zip.ts` 把整个压缩包读入内存，并同步调用 `fflate.unzipSync`；没有压缩包大小、单个条目大小或解压总量限制。
- 画布与素材导入均直接调用 `readZip`，随后还会解析包内 JSON 并并发处理媒体。

攻击前提：用户主动选择攻击者提供的导入文件。导入逻辑运行在用户浏览器，本问题不会直接耗尽服务端资源。

影响：高压缩比或大量条目可使浏览器标签页占满内存、卡死，或在解压结果被 JSON／图片处理后继续放大资源消耗。

修复方向：改用可统计解压进度和累计输出的流式解压，或先审计 ZIP 中央目录再逐项解压；压缩包、单文件及总解压大小阈值需要先确认。超限时在任何文件上传前拒绝，并确保清理部分状态。验收使用隔离生成的小型 ZIP 炸弹样本与正常导出文件，不测试生产数据。

## SEC-12：数据库业务数据没有用户级容量治理

证据：

- `server/internal/platform/ops.go` 的 `enforceStorageQuota` 只统计 `media_objects`，没有统计 PostgreSQL 中的数据。
- `server/internal/platform/content.go` 的偏好接口无业务频控且接受任意 JSON 对象并按键合并；文本素材接口也没有业务频控，`assetInput.Content` 没有字段长度校验。画布快照只要求 `nodes`、`connections` 是数组，内部 JSON 结构和累计字节数不受限。
- 全局请求体上限为 `MAX_UPLOAD_BYTES` 默认 50 MiB。它限制单个请求，不阻止用户持续提交多个偏好键、文本素材或不同画布快照以累积数据库数据。

攻击前提：普通登录账号可以反复调用上述接口；是否最终影响全站可用性取决于数据库磁盘和运维监控，但接口没有按用户或业务数据量阻止累计写入。

影响：PostgreSQL 膨胀、备份增长、昂贵查询和磁盘耗尽。这里描述的是数据库容量治理缺失，并不意味着现有媒体存储配额承诺覆盖 PostgreSQL。

修复方向：确定 PostgreSQL 用户数据计量范围、每用户限额和清理／拒绝策略，并给无频控写接口设计账号级频控。任何新大小限制、配额与频控阈值需先确认适用入口、默认值和超限行为。验收应在隔离数据库验证并发写入不能超卖配额、合法更新仍可用、拒绝后不会留下半写入数据。

## SEC-13：高危操作证明缺少失败尝试频控

证据：

- `server/internal/platform/security.go` 的 `requireSecurityProof` 和 `verifySecurityProof` 执行 Argon2 密码校验与可选 MFA 校验，但没有在验证函数内部频控。
- 管理后台多个高危写接口调用该校验；它们没有在调用点统一使用 `rateLimit`。同文件的用户安全设置和 MFA 登录则有按用户限流，表明覆盖范围并不一致。

攻击前提：攻击者已拿到管理员有效会话，或能从该会话上下文提交请求。仅有普通用户账号不能通过 `/api/admin` 鉴权。

影响：密码尝试可持续进行；每次 Argon2 校验也会占用 CPU，频繁请求可拖慢 API。它不会使未知密码在一次请求内被绕过。

修复方向：按用户／会话对连续失败的二次验证请求做频控，并对正确校验成功后是否重置计数作一致处理；在 Redis 不可用时沿用当前限流策略 fail closed。失败次数和窗口值属于新的行为阈值，确认前不实施。验收应模拟错误密码、错误或重用 MFA 码、并发请求、跨实例和 Redis 故障，不得让拒绝请求发生写入。

## SEC-14：第三方画布插件以站点页面权限运行

证据：

- `web/src/components/canvas/canvas-plugin-manager-modal.tsx` 允许用户输入第三方插件 URL；点击安装后会立即安装并启用，没有可见的代码来源确认步骤。
- `web/src/lib/canvas/plugin-loader.ts` 将下载文本放进 Blob，再以动态 `import()` 执行模块，并调用插件 `setup`。插件代码不是隔离 iframe 或沙箱上下文。
- 已启用插件会从本地持久化的 source 恢复并执行；来源更新由用户明确点击更新触发。

攻击前提：用户主动从不可信 URL 安装插件、启用不可信本地插件，或官方插件仓库／发布源被接管。没有证据表明普通远程网页可在不经过插件安装步骤时把代码注入已登录画布。

影响：插件运行在平台页面同一 origin，可读取当前页面暴露的数据、使用浏览器会话向平台 API 发请求，并向第三方发送其读取到的内容。这是高权限插件信任边界，不应把“成功导入并显示名称”当作安全校验。

修复方向：安装和升级前明确展示发布者、来源域名与将获得的页面权限；对官方包使用签名／固定摘要并在发布源校验，升级不得静默替换已信任内容。若产品需要安装不受信任代码，采用隔离执行模型并只通过最小消息接口开放能力。验收以无害 canary 插件验证来源变化、升级和权限确认，不读取真实用户数据。

## 已检查的保护与范围限制

- 支付通知经过提供商 SDK 验签，核对订单、金额、支付方式；支付宝／微信还校验各自商户信息，微信校验 CNY。浏览器回跳不作为到账依据。
- 充值使用订单行锁、钱包锁、不可变账本唯一约束与数据库事务；返利在真实充值入账事务中执行，兑换码和签到不触发返利。本轮没有发现通过并发重复通知直接重复入账的路径。
- 金额采用整数微元，充值转换为分后再入账；未发现普通用户可以直接提交余额或修改模型价格。
- 外部请求在实际拨号时解析并检查 IP，阻断内网／保留地址；携带密钥的请求拒绝跟随重定向。媒体读取、画布与工作区接口均有归属／成员校验，SVG／Markdown 使用 DOMPurify，HTML 节点使用不含 allow-same-origin 的 sandbox。
- 本地 Agent 监听回环地址，除 health／config 外要求连接 Token，config 不返回 Token。这不能代替对已授权插件和本地环境的信任管理。
- 未读取生产配置、真实账本和供应商扣费记录；依赖审计只针对本地锁文件，未核对生产镜像的实际安装内容。不能证明历史没有损失。若要核查历史，应对比取消任务的输出、供应商账单、`calculated_micros > billed_micros`、兑换码发行与管理员创建记录，以及渠道目的地址变更记录。
