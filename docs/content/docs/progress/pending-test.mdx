### Round 1 improvements (backend reliability, security, frontend toolchain) pending verification

- Unified channel availability: after marking a channel as auto-disabled or disabling all of its keys, its models must disappear from the user model list and return once the channel is saved back to "enabled". Scheduling, quoting and channel debugging share the same rule.
- Cancel propagation: start an image task and cancel it immediately; the upstream request must be interrupted, the task must end as canceled with the full hold refunded, and no upstream cost may be recorded.
- Requeue on shutdown: restart the API while a task is running (`docker compose restart api`); the task must return to the queue and continue instead of failing or refunding. `SHUTDOWN_GRACE_SECONDS` controls how long shutdown waits for in-flight tasks.
- Key rotation: follow the four steps in README "轮换渠道加密密钥"; `canvas-server rotate-keys` prints the re-encrypted row count per table. Channel keys, payment config, SMTP password, TOTP secrets and task channel snapshots must keep working after rotation and after removing `CHANNEL_ENCRYPTION_KEY_PREVIOUS`.
- Second-factor confirmation: editing payment channels, resetting a password, adjusting a balance, clearing request logs, saving platform or mail settings and changing a user role must first show a "安全验证" dialog asking for the current password; canceling it must abort the action. Admins with two-step verification also enter a code.
- Write rate limits: more than 10 redemptions per user per minute must return 429 with a `Retry-After` header.
- Admin audit: every write above must add an `http.<METHOD> <route>` row to the audit list with query, status and requestId in its detail (never the request body).
- Password rules and session renewal: registering or changing a password to the username or to digits only must be rejected in the form and by the API (`weak_password`); refreshing with less than half of the session left must extend the cookie to a full session.
- Pagination: user management paging and filters (keyword, role, status) must return correct rows and totals; canvas lists beyond 200 items must show "加载更多"; the usage statistics page must default to the last 30 days.
- User-side data layer: filters, paging and refresh on the usage log and personal statistics pages must behave as before, and switching accounts must never show the previous account's data.
- Observability: with `METRICS_ADDRESS=:9090` the `/metrics` endpoint must expose `ic_http_requests_total`, `ic_tasks_queued` and friends; `/ready` returns 503 until startup completes and 200 afterwards; `LOG_FORMAT=json` switches logs to JSON, and access plus 500 error logs carry a requestId.
- Frontend toolchain: `npm run build` runs tsc and eslint first (0 errors); `npm test` uses vitest with 65 passing cases.
- Error fallback: making a page throw (or switching routes while an old build's chunk is stale) must show "页面出现错误" with a reload button instead of a blank page.
- Canvas interaction regression (verify carefully after the project.tsx split): dragging, zooming, box selection, connecting, copy/paste, undo/redo, Delete, Escape, image upload drag-and-drop, image node generation, text node generation, batch generation, retry after failure, and resuming in-flight tasks after a refresh.

- 模型状态页改为按渠道真实状态推导可用性：渠道未启用、已自动停用、冷却中或无可用 Key 记为不可用，其余记为可用；模型在至少一个渠道可用且存在不可用渠道时显示「部分可用」。接口不再返回 `checkedAt`，也不再出现「待检测」状态。`uptime` 与最近 40 次记录仍来自真实任务。
- 渠道真实流量失败独立计数（`018_request_failure_tracking.sql` 新增 `channels.consecutive_request_failures`）。只有超时、上游异常和流中断计入；限流靠冷却自愈，鉴权失败由 Key 状态处理，两者都不计入。
- 连续失败达到平台设置阈值（默认 10 次，可配置 0-100，填 0 关闭）时渠道自动停用并通知管理员；**没有任何自动恢复路径**，需要管理员在渠道编辑中保存为「启用」，保存为启用会同时清除自动停用状态、失败计数与故障冷却，恢复后立即可接单。

- 平台设置新增「连续调用失败自动停用阈值」，默认 10；「任务最多尝试次数」补充 10 次上限校验（此前只有下限 1）。

### 任务执行协程 panic 防护待验收

- 后端任务 worker 协程执行任务时不再因单个任务 panic 退出整个进程（此前 gin 的 recovery 只覆盖 HTTP 请求，worker 协程异常会直接打崩服务）。
- panic 发生时记录任务编号、异常信息与完整堆栈，并把该任务租约提前到期（`deadline=now()`），交由既有恢复循环接管：可重试的按原逻辑换渠道重试，不可重试的按超时失败退回冻结余额。
- 验收点：服务在任务执行异常场景下保持存活、其余任务不受影响；异常任务在数秒内被恢复循环接管并最终成功或退款，不会长时间停留在 running 状态。
